# ADR-0003：真实数据与 OAuth 优先的无状态首发

状态：Accepted；2026-09-22 澄清首发持久化边界

日期：2026-09-12

决策人：产品负责人

替代：ADR-0002 中“P2 必须先完成 Sites D1/R2 持久提交后才能进入真实数据链路”的阶段顺序。ADR-0002 的快照信任边界、服务端受信字段和不可变语义继续有效。

## 问题

生产环境很可能迁移到阿里云，D1/R2 未必是最终存储。继续把 Cloudflare 持久化集成作为 Timeline、真实项目和公司 OAuth 的前置，会推迟最重要的真实生产链路。

## 决定

> 后续澄清（2026-09-22）：本 ADR 的“无跨会话持久化”只适用于快照包、生成运行记录、消息快照引用和缓存，不适用于真实项目聚合。DAO tag 准入需要服务端可信保存项目 ID、名称、tag、上下文和对话；该最小项目持久化是生产前提。交付顺序亦调整为先收口 Phase 0 真实 DAO OAuth，再确认 DAO tag 契约和完成项目授权。当前顺序以 `docs/PRODUCTION_RELEASE_PLAN.md` 为准；下列条款保留 9 月 12 日决策原文作为历史记录。

1. 首发优先完成 GUI、快照协议、文本模型和自由对话生成快照的稳定基线，再依次接入 Timeline Agent Support、真实项目数据和公司 OAuth。
2. 首发允许无缓存、无跨会话持久化。快照可以只在当前响应／会话中存在；刷新、历史回放和模型离线回放不作承诺。
3. D1/R2 实现保留为可选存储适配器原型，但不作为首发或 Timeline 接入的阻断项。
4. 生产运行时通过平台适配层部署，优先评估阿里云；快照外层协议、校验器和 Agent 生成逻辑不依赖具体云存储。
5. 首发必须使用真实 OAuth 身份、服务端项目授权和真实 Timeline 只读数据。dummy 只能留在测试／明确演示入口。
6. 持久化先于缓存在发布后实现：先恢复稳定引用和历史回放，再根据真实延迟与 token 成本实现查询复用、TTL 和各级缓存。

## 后果

- 可以更早验证真实用户与真实数据的产品价值，并避免为可能被替换的云存储提前投入。
- 首发刷新后可能丢失生成结果，也不能在模型离线时回放；界面必须明确表达这一限制。
- 无持久化不能削弱当前请求内的身份、权限、来源、完整性和 H5 隔离校验。
- 当前 D1/R2 代码不删除，以存储接口测试和未来迁移参考的身份保留；是否进入阿里云版本由后续存储选型决定。

## 验证

以 `docs/PRODUCTION_RELEASE_PLAN.md` 的首发阻断门槛为准。发布前必须在阿里云预发布环境跑通真实 OAuth、DAO 项目准入、持久项目、真实数据读取、模型生成、快照校验与 viewer 展示的完整链路。
