# 并发、多用户隔离与定时自动化审查 · 2026-09-22

结论：当前实现可作为单实例、少量受控用户的本地验证基线；**不能按现状开放多用户生产访问，也不能把现有 `/api/chat` 直接接到定时器**。生产首发仍按 `docs/PRODUCTION_RELEASE_PLAN.md` 的 Phase 0–5 顺序执行。定时自动化在首发验收后可做第一版，但先限定为只读文本任务；自动写入与自动快照分别需要额外授权和持久化验收。

本审查覆盖当前源代码和已存在的发布计划；没有运行真实 DAO、DeepSeek、Timeline、云环境负载测试，也没有写入第三方系统。审查前工作区已有未提交的文档修改，本文不代表这些修改已经经过部署验收。

## 需要处理的问题（按优先级）

1. **P0，生产准入缺失。** `server/api.mjs:116–126` 接受浏览器自报的项目名、项目 ID 与上下文，`src/web/app.js:219–220` 直接发送这些值。只有登录身份和项目 ID 格式检查，没有服务端项目存在性、DAO tag 准入或可信上下文加载。当前演示壳在 `src/web/project-directory.js:8,30` 产生会重用的 `local-1` 等 ID。快照原型以 `actorId + projectKey` 归属（`src/platform/store.mjs:110–114`），与共享项目的 `tenantId + projectId + actorId` 需求不同。必须先落地可信项目聚合、服务器 UUID、项目级授权和每个入口的授权检查，再开放多人共享项目。
2. **P0，秘密可跨数据源发送，且已知秘密可能进入模型。** `src/platform/context-runtime.mjs:47–53` 将一个项目上下文的所有秘密和 URL 装进同一配置；`src/agent/tools.mjs:132–159` 用全局 vault 替换任一已允许 URL 的请求。内存 fetch 反例：A 的密码引用被放进 B 的 Authorization，宿主向 B 发送 A 的明文密码。`src/agent/tools.mjs:56–66,171` 只按响应 JSON 字段名脱敏；若已知密码出现在 `message` 或纯文本响应，仍会原样交给模型。需要按数据源绑定秘密引用、限制可用方法和目标，并对返回模型的所有字符串先替换已知秘密。
3. **P1，出站目标边界不足。** `src/platform/context-runtime.mjs:5–13` 和 `src/agent/tools.mjs:69–77,159` 校验 HTTPS origin/path，但接受 `https://127.0.0.1/` 等私网或回环目标；内存 fetch 反例确认请求能到达执行器。真实网络可达性和 TLS 成功未测试。生产需要服务器管理的出站策略、DNS 解析后地址检查及代理/安全组约束；合法内部系统应显式纳入受控范围，不能依赖模型或客户端提供的 URL 扩权。
4. **P1，写入审计与执行身份未绑定。** `src/agent/tools.mjs:100–105,144` 只验证 change-set 的 `actor` 非空，`src/agent/run.mjs:31` 调用 Runtime 时不传 `actorId`。内存 fetch 反例中模型提交 `actor: "another-user"` 被转发。宿主应写入或核对当前 DAO 用户 ID；定时任务还要区分调度者、被授权执行身份、触发时间和实际操作者。真实目标系统是否覆盖 actor 尚未验证。
5. **P1，并发是每用户进程内计数，缺少整机资源上限。** `server/api.mjs:6,93–103` 每用户每分钟最多 20 次、同时最多 2 次。内存阻塞 Runtime 反例中，6 个用户同时启动 12 个运行全部获准，同一用户第 3 个才获 429；跨实例计数也不共享。每次运行会启动 Claude Code 和 MCP 子进程并占用内存、临时文件、外部模型额度（`server/claude-runtime.mjs:106–108,160–175,211–221`）。生产需基于容量测量设置进程总量、每租户/项目/用户并发、排队上限、预算和过载响应；计划中的单实例首发也要有整机上限。
6. **P1，取消不是硬资源边界。** `server/claude-runtime.mjs:111–112,132–150` 只向直接子进程发送 SIGTERM，等待其 close 才释放请求。已经 aborted 的 signal 没有在 spawn 前拦截，SIGTERM 不退出也没有强制升级；MCP 后代进程与临时目录回收没有独立保障。内存 fake-child 反例：预先 abort 的请求仍 spawn 一次，未调用 kill。生产应在启动前检查取消、给每次执行设硬墙钟时间、先 TERM 后 KILL，并清理进程树和工作目录；用真实子进程反例验收。
7. **P1，现有幂等不能支持无人值守重试。** `src/web/app.js:220` 使用 `auto` 模式；`server/api.mjs:140–150` 只对显式 `snapshot` 在模型前登记 run，`server/api.mjs:180–190` 对 auto 在模型执行后才登记；文本和无存储路径完全不登记。相同 key 可重复扣模型费用、读取或触发 change-set/commit。`src/platform/store.mjs:44–52` 的 staging 没有租约过期或恢复。自动化必须先持久登记 `scheduleId + plannedFireTime` 唯一键、执行租约、状态与重试策略，再调用模型；外部写入要有目标系统认可的业务幂等键和结果回读。调度器自己的“单实例并发 1”不能保证业务操作只发生一次。
8. **P2，当前进程隔离是逻辑隔离。** 每次运行有独立临时目录和 0600 文件、禁用大多数内置工具与无会话持久化（`server/claude-runtime.mjs:160–195`），这是积极基线；子进程仍与宿主同 UID，并继承 `process.env`（`:198–209`），无容器/OS 租户隔离。当前没有证据表明模型可突破工具权限；部署时仍应收窄子进程环境、文件和出站权限，并对并发任务施加 CPU/内存配额。

## 定时自动化的可行路径

技术上可行。阿里云 SchedulerX 提供 Cron/固定频率、重试和作业/应用并发控制，也支持 HTTP 或运行在 VPC 内的 agent；这些解决“何时触发”和部分流控，不提供本项目的项目授权、业务去重与结果归属。第一版建议外部调度器只发送不含秘密的 `scheduleId + plannedFireTime` 到受保护任务入口；服务端从持久项目聚合读取上下文，校验该项目和任务的当前授权，原子登记 run 后调用与聊天共用的受控 Agent 执行器。任务状态、简短结果、错误码、耗时、模型用量和审计字段持久化；执行失败、超时、任务关闭或项目删除后不能继续重试。网页可按项目读取获准任务和运行结果。

建议首版只允许只读文本任务，并区分“谁创建/批准任务”和“运行时代表谁访问数据源”。若公司 OAuth 只提供短期用户 session，调度器不能借用浏览器 cookie；需要 DAO 确认服务身份/委托授权及撤权语义。计划发布后再做此阶段，至少通过项目共享准入、秘密按源隔离、全局配额、子进程硬回收和持久运行去重。定时生成快照还需要不可变快照包与结果引用持久化；定时外部写入还需要单独的明确授权、目标端幂等与写后回读。

## 验证与限制

- `npm run check`：52 项 Node 测试通过、构建通过、7 个 fixture 校验通过。
- `npm run test:e2e`：Chromium/WebKit 共 32 项通过。首次受沙箱监听限制失败，获准启动本地测试服务器后重跑通过。
- 审查专用内存反例：6 用户各 2 个并发请求全部被接纳；同用户第 3 个返回 429；未注册项目与回环 HTTPS 上下文被接纳；相同 key 在无存储路径启动两次；A 密码可发送至 B；任意非空 actor 被转发；预先取消的 fake child 仍被 spawn。所有 HTTP 调用均使用本地 stub，无真实外网请求。
- 补充并发隔离验证：用四个真实本地 Node 子进程代替 Claude Code，其中两个走并发 HTTP handler；每次运行得到不同 PID、临时目录和请求级秘密配置，A/B 响应各回到自己的请求，临时目录结束后清理。该验证只证明当前正常完成路径的进程与响应映射，不是 Claude Code、恶意模型或操作系统沙箱的端到端证明。
- 一位普通审查代理完成安全隔离检查；另一位普通审查代理提供了并发/幂等反例与行号，随后因使用额度中断。主审查已独立复核关键结论。这不是专用 Security Review 或 Bugbot 产品运行。真实 DAO 回调、云上并发容量、外部目标 TLS/网络可达性、写入实际审计结果和定时服务身份均未验收。
